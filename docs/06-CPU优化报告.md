# M1 · CPU 推理极限优化报告

测量日期：2026-09-11 · 平台：`L40S-1-gpu`（2× Intel Xeon Platinum 8352V，144 线程，502 GB）
所有数字若无特别说明，均为本机实测，非引用。

---

## 0. 术语表（阅读前必看）

| 术语 | 全称 | 含义 | 决定什么 |
|---|---|---|---|
| **pp512** | **p**rompt **p**rocessing, 512 tokens | **预填充**：读入输入、建立 KV cache。512 个 token **并行**处理（批量矩阵乘） | **首字延迟**（TTFT） |
| **tg128** | **t**ext **g**eneration, 128 tokens | **解码**：逐个生成 128 个输出 token，每 token 一次完整前向 | **出字速度** |
| **TTFT** | time to first token | 从提交请求到第一个 token 出现 | 交互响应感 |
| **KV cache** | key/value cache | 注意力机制的键值缓存，随上下文线性增长 | 显存/内存占用 |
| **GGUF** | — | llama.cpp 的模型文件格式，内含量化权重 | — |
| **Q4_K_M / Q8_0 / IQ4_XS** | — | 不同的量化方案（4-bit K-quant / 8-bit legacy / 4-bit i-quant），**反量化计算路径不同**，CPU 上性能差异很大 | 见 §4A.1 |
| **NUMA** | non-uniform memory access | 多路 CPU 的内存局部性。跨节点访问延迟显著更高 | 见 §3.4 |
| **SMT / 超线程** | simultaneous multithreading | 一个物理核暴露两个逻辑线程。AVX512 会占满物理核，兄弟线程互相拖累 | 见 §3.1 |

### 一个 agent 任务的总耗时

```
总耗时 ≈ prompt_tokens / pp速率 + output_tokens / tg速率
```

以「读 2k token 日志 → 输出 100 token 摘要」为例：

| 模型 | 预填充 | 解码 | **总计** |
|---|---:|---:|---:|
| Qwen3-8B @16 线程 | 2000/80.75 = 24.8 s | 100/11.05 = 9.0 s | **33.8 s** |
| MiniCPM5-2B IQ4_XS @12 | 2000/290 = 6.9 s | 100/37.9 = 2.6 s | **9.5 s** |

**本场景的负载两段都吃**（读日志用 pp、写摘要/调工具用 tg）——这是判定 OpenVINO 不可用的根据（§4B：pp 相当但 tg 慢 4 倍）。

## 1. 硬件天花板（决定了优化空间的上限）

| 项 | 实测 | 含义 |
|---|---|---|
| CPU | 2× Xeon Platinum **8352V**（Ice Lake-SP）@ 2.10 GHz | — |
| 核心/线程 | 36 核/路 × 2 路 = 72 物理核，**144 线程** | — |
| NUMA | **2 节点**：node0 = CPU 0-35,72-107；node1 = 36-71,108-143 | 跨 socket 访问是陷阱 |
| ISA | `avx512f/bw/cd/dq/vl/vbmi/vbmi2/vnni/bitalg/vpopcntdq/ifma` | — |
| **AMX** | **缺失**（`grep -c amx /proc/cpuinfo` = 0） | ★ **INT8 峰值被压低一档** |
| L3 | 55 MB | 装不下 8B Q4 的 4.7 GB 权重 → 必然内存带宽受限 |
| 内存 | 502 GB | 容量不是约束 |

**AMX 缺失是本报告最重要的一条前置事实。** Intel 最强的 CPU 矩阵加速单元（AMX_INT8/AMX_BF16）在 Ice Lake 上不存在，只有 AVX512-VNNI。这直接否决了下文 §3.3 中"用 INT8 量化换吞吐"的常规思路。

## 3. 逐项结果

### 3.1 线程数（T1）— 最大单项收益，且与直觉相反

Qwen3-8B Q4_K_M，原生构建，`-p 512 -n 128 -r 2`：

| 线程 | pp512 (t/s) | tg128 (t/s) | 相对 36 线程 |
|---:|---:|---:|---:|
| 8 | 56.76 | 10.17 | 1.71× |
| **16** | **80.75** | **11.03** | **1.86×** |
| 24 | 66.54 | 8.02 | 1.35× |
| 32 | 62.43 | 6.58 | 1.11× |
| 36 | 60.30 | 5.94 | 1.00× |
| 48 | 48.87 | 3.50 | 0.59× |
| 72 | 31.61 | 2.41 | 0.41× |
| **144** | **5.14** | **0.00** | **0.00×** |

**甜点是 16 线程**（占物理核数的 22%，占单 socket 36 核的 44%）。超过后单调恶化，144 线程时**几乎完全瘫痪**。

原因：AVX512 会占满整个物理核，超线程的兄弟线程只能空转争抢；跨 NUMA 节点的内存访问进一步放大惩罚。16 线程恰好落在一个 socket 内且不触发 SMT 争抢。

> 这也是我最初用 Ollama 默认 36 线程测出 2.31 t/s 的主因——**不是 PRoot，是线程数**。

### 3.2 原生构建（T2）

| 构建 | pp512 | tg128 |
|---|---:|---:|
| 系统 gcc-7.5（失败） | — | — |
| PRoot + gcc-11（`build-cpu`） | 79.80 ± 5.79 | 10.74 ± 0.08 |
| **原生 gcc-8.4 + `-march=native` + LTO** | **76.52 ± 5.58** | **10.98 ± 0.23** |
| 原生复测 | — | 10.83 ± 0.07 |

**两者在噪声范围内相同。** 原生构建的收益（~1.2×，对比 Ollama 自带的 llama.cpp）主要来自版本与编译选项，不来自摆脱 PRoot。

**gcc-8.4 的关键验证**：`-march=native` 解析为 **`icelake-server`** 且 **`-mavx512vnni [enabled]`** —— VNNI 路径确实是开的。

构建踩坑记录（供复现）：
1. gcc-7.5 编不过 → 需 gcc-8+（C++17 的 `<charconv>`、`_mm256_set_m128`）
2. gcc-8 链接 `std::filesystem` 需要 `-lstdc++fs`，且**必须放在链接行末尾** → `-DCMAKE_CXX_STANDARD_LIBRARIES=-lstdc++fs`（`CMAKE_EXE_LINKER_FLAGS` 放行首会被链接器丢弃）
3. gcc-8 的 CTAD 支持不全 → `llama-server` 的 `server-schema.cpp` 编不过；`llama-bench` 与 `llama-cli` 正常

### 3.3 量化（T3）—— 一条被证伪的假设

**假设**（源自 Intel 官方博客）：Q8_0 对齐 x86 INT8 路径（VNNI/AMX），应比 Q4_K_M 更快。

**实测结果（16 线程）**：

| 量化 | 大小 | pp512 | tg128 | 判定 |
|---|---:|---:|---:|---|
| **Q4_K_M** | 4.68 GiB | **77.4** | **10.8** | ✅ |
| Q8_0 | 8.11 GiB | 60.2 | **6.5** | ❌ **慢 1.66×** |

**假设被证伪。** 原因：
1. **本机没有 AMX**，VNNI 的 INT8 优势远小于 AMX
2. batch=1 的解码是**纯内存带宽受限**——Q8_0 两倍的体积直接换算成两倍的内存流量，压倒了计算侧的收益
3. L3 只有 55 MB，装不下任何一个模型的权重

**结论：在这台机器上，量化应优先选小而快的（Q4_K_M），而不是"对齐 INT8 指令"的。**

### 3.4 NUMA（T4）

16 线程下：

| 模式 | pp512 | tg128 |
|---|---:|---:|
| 默认 | **77.4** | **10.8** |
| `--numa distribute` | 74.0 | 10.4 |
| `--numa isolate` | 71.6 | 7.9 |

**无收益，`isolate` 反而有害。** 因为 16 线程本就落在一个 socket 内，内存自然就近分配；显式 NUMA 策略只增加了调度开销。

### 3.5 KV cache 量化（T5）

| 配置 | pp512 | tg128 | 相对内存 |
|---|---:|---:|---:|
| f16（默认） | **77.4** | **10.8** | 1.00× |
| q8_0 | 67.6 | 10.2 | 0.53× |
| q4_0 | 61.2 | 10.1 | 0.28× |

**代价很小（decode −6% / −7%），换来一半到四分之一的 KV 内存。** 对长上下文场景值得开——尤其 Qwen3-32B 要到 131k 必须靠它。

### 3.6 投机解码（T6）—— 决定性结论：合成上限只有 +15%

**这一节经过五轮修正。前四轮的配置有误（见 §3.6.5），最终由「合成接受上限」测试给出不依赖草稿质量的定论。**

#### 3.6.1 ★ 决定性证据：合成接受上限

llama.cpp 提供 `--spec-synth-len`：**用合成决策替代真实验证**，即"假装草稿完美"。这给出了**与草稿质量无关的理论天花板**。

Qwen3-8B Q4_K_M @16 线程（独占运行，`--spec-draft-n-max` 显式设置）：

| 配置 | Prompt (t/s) | Generation (t/s) | vs 基线 |
|---|---:|---:|---:|
| **baseline** | 68.4 | **9.1** | 1.00× |
| K=4, synth=4 | 81.7 | 9.6 | 1.05× |
| K=8, synth=8 | 81.4 | 9.4 | 1.03× |
| K=16, synth=16 | 86.6 | 10.5 | 1.15× |
| K=32, synth=32 | 86.8 | 10.4 | 1.14× |

> **即使给予"完美草稿 + 每次接受 32 个 token"，生成吞吐也只从 9.1 升到 10.5（+15%）。**

**结论：投机解码在这台 CPU 上结构性地无法产生有意义的加速。这个结论不依赖任何草稿模型的质量。**

**为什么我之前判断错了**：我用 `pp8 = 48.7 t/s` 推断"验证 8 个 token 只要 1 次前向的成本"。但那只测的是**提示处理（prompt processing）路径**——它有高效的批量实现。**投机验证路径并没有拿到同等的批量摊薄**，其采样/接受逻辑与 KV 管理带来逐 token 的 CPU 开销，吃掉了批量收益。

#### 3.6.2 各方法的实测（全部无效）

| 方法 | 草稿来源 | Prompt | Generation | vs 基线 |
|---|---|---:|---:|---:|
| baseline | — | 71.2 | 10.4 | 1.00× |
| `ngram-simple` | n-gram 统计 | 48.3 | 10.6 | 1.02× |
| `ngram-map-k` | n-gram 统计 | 76.7 | 9.8 | 0.94× |
| `ngram-mod`（官方 `--spec-default`） | n-gram 统计 | 82.8 | 9.5 | 0.91× |
| `draft-simple` | 外部异族小模型（Qwen3.5-0.8B） | 66.6 | 9.7 | 0.93× |
| `draft-dspark` | 外部伴随检查点（3.5 GB） | 75.4 | 9.8 | 0.94× |
| **`draft-eagle3`** | **官方为 Qwen3-8B 发布的 EAGLE-3** | 55.0 | **5.4** | **0.59×** |

**EAGLE-3 是唯一"按官方标准配置"跑通的方法**（检查点 `AngelSlim/Qwen3-8B_eagle3`，官方命令格式转换，官方参数），结果**慢 1.7 倍**。原因是草稿为**单层 bf16 模型（799 MB）**，而本机 Ice Lake **无 AVX512-BF16**，CPU 上 bf16 无向量加速，多跑一个模型的开销超过收益。

#### 3.6.3 真自投机（层跳过）—— 无法用现成工具验证

DSpark/EAGLE-3 虽为目标专属，但仍是**独立模型**。真正的自投机（LayerSkip / [CLaSp](https://arxiv.org/abs/2505.24196) / [KnapSpec](https://github.com/kaist-flexml-lab/knapspec)）用的是**同一模型的内部层组合**。

**llama.cpp 没有此能力**：`grep -rniE "layer_skip|layerskip|early_exit|n_skip_layer"` → 无输出；[discussion #10787](https://github.com/ggml-org/llama.cpp/discussions/10787) 至今开放。

**但 §3.6.1 已使这个问题失去意义**：合成上限只有 +15%，层跳过再优秀也无法突破这个天花板。**故不建议投入移植工作。**

#### 3.6.4 n-gram 型的适用边界

官方文档把 `ngram-mod` 列为 `--spec-default`，并指出适用场景包括"**推理模型（需要把思考复述进最终答案）**"与"**摘要**"。这类方法**零草稿成本**，在**高重复**负载上确实有效。

本机实测无收益，是因为测试提示产生的**新颖思考文本**没有 n-gram 可命中。**若某个具体工作流确实高度重复（如逐行改写代码、复述式摘要），仍值得单独复测**——它没有草稿开销，只有收益可能。

#### 3.6.5 我犯的配置错误（记录以免重犯）

| 错误 | 正确做法（官方 `docs/speculative.md`） |
|---|---|
| 用 `llama-cli` | 示例统一用 **`llama-server`** |
| 未加 `-fa on` | DFlash/DSpark **明确要求 `-fa on`** |
| 未加 `--jinja` | 示例全部带 `--jinja` |
| 未设 `--spec-draft-n-max` | **默认仅 3**，合成接受测试的 K 因此未生效 |
| 跨族乱选草稿（Qwen3.5-0.8B 配 Qwen3-8B） | 用**同 tokenizer / 官方发布的专属检查点** |
| 未验证草稿是否真的激活 | 应检查日志中是否有 `failed to load draft model` |
| EAGLE-3 检查点是 `pytorch_model.bin` | 需先转 safetensors 再转 GGUF，否则 `n_tensors = 0` |

## 4. 跨模型吞吐（最优配置：原生 + 16 线程 + Q4_K_M + f16 KV）

| 模型 | 参数 | pp512 (t/s) | tg128 (t/s) | tg @8线程 |
|---|---:|---:|---:|---:|
| Qwen3.5-0.8B | 0.75B | **382.0** | 48.2 | **51.6** |
| MiniCPM5-2B | 2.52B | 226.5 | 27.3 | **31.0** |
| Granite 4.2 3B | 3.66B | 148.8 | 19.6 | — |
| Qwen3-8B | 8.19B | 75.3 | 10.0 | — |
| Qwen3-32B | 32.8B | 17.4 | 2.7 | — |

**观察**：
- 小模型（≤3B）在 **8 线程**下解码更快（SMT 争抢更少），大模型 16 线程更均衡
- 吞吐大致与参数量成反比，符合内存带宽受限的预期
- **Qwen3-32B 在 CPU 上只有 2.7 t/s** —— 读一份 2k token 的日志需 **~13 分钟**，事实上不可用

### 4.1 响应时间估算（按"prompt/prefill + output/decode"）

输出长度取实测值（工具调用测试的平均输出 token）：

| 任务 | Qwen3.5-0.8B | MiniCPM5-2B | Granite 3B | Qwen3-8B |
|---|---:|---:|---:|---:|
| 状态查询（20 tok prompt / ~35 out） | **~0.8 s** | ~2.2 s | ~3.0 s | ~3.4 s |
| 读 2k 日志摘要（2000 / 60） | **~7.7 s** | ~11.0 s | ~25.4 s | ~32.6 s |
| 读 1k 摘要（1000 / 60） | ~4.2 s | ~6.7 s | ~17.5 s | ~19.3 s |

对比优化前（Ollama 默认 36 线程）：
- Qwen3-8B 读 2k 日志：**49.9 s → 32.6 s**
- Qwen3.5-0.8B 读 2k 日志：**13.2 s → 7.7 s**

## 4A. MiniCPM5-2B 完整表征（★ 选定模型）

MiniCPM5-2B 是最终选定的**值班员**模型（同时承担确定性操作与智力操作），故做完整扫描。

### 4A.1 量化矩阵（原生 ggml，pp512 / tg128 t/s）

| 量化 | 大小 | t=8 pp | t=8 tg | t=16 pp | t=16 tg |
|---|---:|---:|---:|---:|---:|
| **IQ4_XS** | **1.36 GiB** | 216.5 | 31.8 | 257.4 | **31.2** |
| Q4_0 | 1.41 GiB | 174.5 | 31.5 | 230.7 | 30.8 |
| Q4_K_M | 1.45 GiB | 183.4 | 31.0 | 226.5 | 28.3 |
| Q5_K_M | 1.78 GiB | 69.9 | 23.7 | 91.4 | 23.9 |
| Q8_0 | 2.49 GiB | 140.4 | 18.2 | 199.8 | 19.1 |

**反直觉的赢家：IQ4_XS**——最小、预填充最快、解码并列最快。
我原本预期 i-quant 的查表路径在 CPU 上更慢，**实测恰恰相反**。

**Q5_K_M 是陷阱**：预填充暴跌到 91 t/s（Q4_K_M 的 40%）。K-quant 的反量化在预填充阶段代价极高。

### 4A.2 线程谱（IQ4_XS）

| 线程 | 4 | 6 | 8 | **12** | 16 | 24 | 32 |
|---|---:|---:|---:|---:|---:|---:|---:|
| pp512 | 114.0 | 154.0 | 213.5 | **290.3** | 249.7 | 214.0 | 192.1 |
| tg128 | 20.9 | 26.7 | 31.8 | **37.9** | 31.3 | 23.3 | 19.1 |

**甜点是 12 线程**（不是 8B 模型的 16）。**最优线程数随模型变小而下降。**

```
最优配置：MiniCPM5-2B + IQ4_XS + 12 线程 + f16 KV
→ pp512 = 290 t/s，tg128 = 37.9 t/s
```

比初始配置（Q4_K_M @16 线程：226 / 28.3）**快 28%**。

### 4A.3 KV cache 量化（Q4_K_M, t=16）

| KV | pp512 | tg128 |
|---|---:|---:|
| f16 | 224.9 | 28.3 |
| q8_0 | 196.8 | **28.0** |
| q4_0 | 160.4 | 27.5 |

**q8_0 解码几乎无损（−1%），预填充 −12%。** 需要长上下文时值得开（内存减半）。

## 4B. OpenVINO 后端：★ 测通了，但不可用

**这是本报告里最难打通的一条链路**，历经四层阻塞：

| 层 | 阻塞 | 解法 |
|---|---|---|
| 1 | llama.cpp 要求 OpenVINO **2026.3.1**，但 wheel 是 `cp310+` | 改用 Python 3.11 建 venv |
| 2 | 2026.3.1 是 `manylinux_2_28`（需 glibc ≥ 2.28），宿主 glibc 2.27 | `pip install --platform manylinux_2_28_x86_64 --only-binary=:all: --target` 绕过检查 |
| 3 | 运行时需要 glibc 2.28+ | **全链路搬进 PRoot**（rootfs glibc 2.35） |
| 4 | PRoot 内 `find_package(OpenCL)` 失败 | 把宿主 `/usr/include/CL` 与 `libOpenCL.so*` 绑进 PRoot |

最终 **构建成功**（`BUILD_EXIT=0`），设备识别正常：

```
OPENVINO0: OpenVINO Runtime (514992 MiB, 514992 MiB free)
```

### 结果：预填充相当，解码慢 3.4–4.4 倍

| 模型 / 量化 | OpenVINO pp512 | OpenVINO tg128 | 原生 ggml tg128 | 解码慢 |
|---|---:|---:|---:|---:|
| MiniCPM5-2B Q4_K_M | 256.2 | 6.80 | **28.25** | 4.2× |
| MiniCPM5-2B Q4_0 | 271.6 | 6.94 | **30.80** | 4.4× |
| MiniCPM5-2B Q8_0 | 227.8 | 5.69 | **19.14** | 3.4× |
| Qwen3-8B Q4_K_M | 103.3 | 2.94 | **10.98** | 3.7× |
| MiniCPM5-2B **IQ4_XS** | **失败**（`failed to decode prompt batch, res = -3`） | — | 31.20 | 不支持 |

**判定：不可用。**
- OpenVINO 为**批量吞吐**优化（图编译 / 算子融合），单 token 解码的每次调用开销很高
- 而本场景负载（生成报告、工具调用、日志摘要）**全是解码密集型**
- **i-quant 不在其支持列表内**（官方列表：FP16 / BF16 / Q8_0 / Q4_0 / Q4_1 / Q4_K / Q4_K_M / Q5_K / Q6_K），而 i-quant 恰是原生后端下最快的
- 官方文档自述"性能与内存优化 work in progress"，且**验证目标是 Intel Core Ultra AI PC，不含 Xeon 服务器**

2. **MiniCPM5-2B 在"中止实验"上返回空调用** —— 安全敏感操作失败
3. 失败集中在两类：**需要理解的意图**（画什么图）和**破坏性操作**（中止、删除）

### 5.2 状态理解与推理（★ 已重测成功）

**测量条件**（修正了首轮的失败）：`llama-server`（非 Ollama）+ `--jinja`，预算 1500 token，**接受 CoT**，评分按全文匹配。

| 模型 | R1 查表（5 事实） | R2 三分类 | R4-ETA | 输出 token | 墙钟 |
|---|---|---|---|---|---|
| **MiniCPM5-2B** | **5/5** ✅ | **3/3** ✅ | **1/1** ✅ | 270 / 118 / 809 | 10.2 / 4.4 / 31.8 s |
| Qwen3.5-0.8B | **0/5** ❌ | 1/3 | 0/1 | **1500**（撞上限） | 32.2 s |
| Granite 4.2 3B | 未产出 | — | — | — | 脚本异常 |
| Qwen3-8B | 未产出 | — | — | — | 脚本异常 |

**两个决定性发现**：

1. **MiniCPM5-2B 在状态理解上全面优于 Qwen3.5-0.8B**，且输出简洁（270 token 对 1500）。
   **0.8B 无法完成"从 digest 提取 5 个指定数值"这类指令跟随任务**——它会一直输出而答不出要点。

2. **`rsn_chars = 0`：llama-server 把 CoT 放在 `content` 里**（不像 Ollama 拆到独立的 `reasoning` 字段）。
   → **思考通道问题在使用 llama-server 时自然解决**，`content` 直接可读，DSH 无需特殊适配。

**首轮测量为何失败**（已定位，见 §7 教训）：用 Ollama 时思考被拆到 `reasoning` 字段且预算不足（300 token），导致 `content` 为空、评分全 0。**不是模型能力问题，是我的测量配置问题。**

### 5.3 绘图能力专项（★ 2026-09-11 实测）

针对"§5.1 里 MiniCPM5-2B 画图到底行不行"的追问，做了三个专项测试（CPU llama-server，IQ4_XS，12 线程）：

## 7. 测量纪律的教训（必须记录）

本轮出现过**三次**结论性错误，都已定位并更正：

1. **PRoot「5 倍惩罚」是假的**。首次测得 PRoot pp512=14.82 vs 原生 75.3，看似重大发现；实际是 PRoot llama-bench 与另一组测试并发运行导致。**串行重测后两者相同（79.80 vs 76.52）。**

2. **投机解码首次基线 1.82 t/s 是假的**，同样源于并发；串行重测为 10.4 t/s。

3. **"投机解码在本机必然无效"的推理是错的**。我用"内存带宽受限"论证它不可能有收益，但 §3.6.1 的批量扫描证明**批量验证有 5.6 倍的结构空间**——推理本身站不住。真实原因是**草稿质量**：异族小模型与 n-gram 都无法预测目标模型的新颖思考文本。

4. **DSpark 测试无效**。日志显示 `dflash requires ctx_other to be set`，草稿很可能从未激活，三组数字几乎相同即为此故。**不能据此断言伴随检查点方法无效。**

**纪律**：
- 所有 CPU 性能数字必须**独占运行**；`llama-bench -r` 只消除机内噪声，不能消除外部并发。长任务前必须确认 `uptime` 负载为空。
- **看到"完全无效果"的结果时，先验证功能是否真的启用了**（DSpark 的教训），再下结论。
- **区分对照组**：外部草稿 ≠ 自投机；n-gram ≠ 层跳过。命名相似不代表机制相同。

## 8. 结论

### 8.1 优化收益总结

| 阶段 | Qwen3-8B tg128 |
|---|---:|
| 初始（Ollama 默认 36 线程） | 5.02 t/s |
| + 原生构建 | 5.94 t/s（1.18×） |
| **+ 16 线程** | **11.03 t/s（2.20×）** |

**总提升 ~2.2 倍，其中线程数贡献了绝大部分。**

### 8.2 但优化改变不了结论

即使拿到 2.2 倍，**Qwen3-32B 在 CPU 上仍只有 2.7 t/s**，读一份 2k 日志要 13 分钟。**"研究员档跑在 CPU 上"这条路线被实测否决** —— 研究员必须用 GPU。

### 8.3 两档部署选型建议（已定稿）

| 部署层 | 承担角色 | 选型 | CPU 延迟 | 依据 |
|---|---|---|---|---|
| **第一层**<br>CPU 常驻 | 值班员 | **MiniCPM5-2B**<br>IQ4_XS · 12 线程 | 状态查询 **2.2 s**；读 2k 日志 11.0 s | R1 **5/5**、R2 **3/3**；131k 上下文；解码 27–31 t/s；KV 每 token 最省；0.8B 在同一任务上 **0/5** |
| **第二层**<br>GPU 按需 | 研究员 | **Qwen3-32B** | — | 工具调用 6/6 唯一全对；CPU 2.7 t/s 不可用 |

**相比初始方案的关键变化**：**三个角色合并为两个**（助理研究员被值班员吸收）——从"三模型两端点"简化为**两模型两端点**。
两个角色的区别只在**职责、工具集与提示**（换 agent 预设），不在模型。
Qwen3.5-0.8B **不采用**（R1 0/5）。

### 8.4 生产部署必须解决的两件事

1. **用 `llama-server` 而非 Ollama**：
   - llama-server 把 CoT 直接放进 `content`，**无需适配思考通道**（实测 `rsn_chars=0`）
   - Ollama 在 PRoot 内**不可靠**（本轮 GPU discovery watchdog 超时并崩溃）
   - 启动参数：`llama-server -m <model>.gguf -t 16 -c 8192 --jinja`

2. **线程数固定 16**（或小模型用 8）：36 线程会损失 1.85×，144 线程会瘫痪。

### 8.5 对"破坏性操作"的最终建议

工具调用实测：只有 Qwen3-8B 达到 6/6，而它在 CPU 上慢 2.7×、上下文仅 40,960。
若为可靠性把值班员换成 Qwen3-8B，代价很大。

**建议：用确定性意图解析兜住破坏性操作**（中止实验、删除请求），使值班员可以安全地选 MiniCPM5-2B：

```
用户输入 → 关键词/正则/模板匹配
         ├─ 命中确定性操作 → 回显确认 → 直接执行（不经过模型）
         └─ 未命中 → 交给 MiniCPM5-2B 处理
```

理由：破坏性操作**失败代价高且完全确定性**，不应依赖任何规模模型的判断；而"可靠"是**工具的属性**，不是模型的属性。
