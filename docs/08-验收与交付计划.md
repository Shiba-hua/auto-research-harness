## 2. ✅ 隔离边界：已解决（源码 + 实测确认）

### 2.1 你的直觉对，但默认值是反的

你说"既要能授权工作区写入，也要能确定只读目录"。**DSH 的原生语义正好是你要的，但方向相反**：

> **不是"工作区可写 + 额外指定只读目录"，而是"工作区可写 + 其余一切皆只读"。**

`@deepseek-ai/dsh-sandbox-local` 的 Linux 配置（`bwrapProfileArgs`，源码原文）：

```js
const args = ["--ro-bind", "/", "/",  // ← 整个文件系统以只读方式绑定
              "--dev", "/dev", "--unshare-pid", "--proc", "/proc", "--die-with-parent"];
if (policy.mode === "workspace-write") {
  args.push("--tmpfs", "/tmp");                          // ← /tmp 是私有 tmpfs
  args.push("--bind", policy.workspaceRoot, policy.workspaceRoot);  // ← 只有工作区可写
}
```

**所以 `/root/siton-tmp/rlvr-l40s-lab` 天然可读、天然不可写——不需要任何额外配置。**

### 2.2 文件工具的隔离在这台机器上**可用**（关键确认）

`@deepseek-ai/dsh-fs-sandbox` 是**进程内的路径判定**，不是内核沙箱：

| 事实 | 来源 |
|---|---|
| `inject = ["sandboxPolicy"]` —— **不注入 `ctx.sandbox`** | 源码 |
| 源码注释自述："This is **containment, not a security boundary**；内核级隔离是 `ctx.shell` 的职责" | 源码 |
| `read-only` 拒绝一切修改；`workspace-write` 仅允许**规范化后落在 workspace 根或平台临时区**的修改；`danger-full-access` 不设围栏 | 源码 |
| 拒绝时返回 `FS_SANDBOX_DENIED`，并附**同轮升级提示** | 源码 |

→ **文件层：读不受限（lab 可读 ✅）、写限于 `/root/dsh-harness` + 平台临时区（✅）、无需任何 runner。**

### 2.3 ⚠️ 但 bash 的隔离在这台机器上**不可用**

实测（`L40S-1-gpu`）：

| 探测项 | 结果 |
|---|---|
| `which bwrap` | **不存在** |
| 内核 | `5.10.0-136.12.0.86.oe2203sp1.x86_64`（openEuler 22.03 SP1） |
| `landlock_create_ruleset(VERSION)` | **-1 / errno 38 `Function not implemented`**（Landlock 需 5.13+，未回移） |
| `unshare --user --map-root-user` | **`Operation not permitted`** |
| `/proc/self/status` | `Seccomp: 2`（filter 模式，1 个过滤器）→ 用户命名空间被 seccomp 挡住 |

DSH 的 Linux runner 链是 **`["bwrap", "landlock"]`**（源码 `PLATFORM_CHAINS`），且 `confine()`
对每个 mode 都返回包装后的 argv——**没有 mode 级的旁路**。两者都不可用 → 抛 `SANDBOX_UNAVAILABLE`。

DSH 源码里自己写明了 fallback（错误信息原文）：

> `Install bubblewrap or run a Landlock-enforcing kernel (Linux) … **otherwise switch the consumer to danger-full-access.**`

### 2.4 由此得出的架构决定

| 决定 | 理由 |
|---|---|
| **值班员不给 bash 工具** | 它只需要只读查询 + 队列 + 绘图，本来就不需要 shell |
| **研究员不给 bash 工具** | `workspace-write` 下每条 bash 都会 fail-closed；给了等于给一个必然报错的工具 |
| **实验执行做成专用工具 `lab-run`** | 见下 |

**`lab-run` 是这次隔离设计的落点**：模型选 run 配置 → 我校验参数 → 由**我的代码**拉起
lab 里**预先存在、已审阅**的入口（`train.py` 等）→ 产物落 `results/`。
模型全程不接触任意 shell。这正好是 07 里"窄契约、幂等、可验证"原则的自然延伸。

### 2.5 ✅ 用 git 可逆性，解掉 shell 隔离不了的两难

原本的两难是「研究员能不能运行自己写的代码」。**你的 git 分支方案把它解掉了**——
不靠"阻止它写"，靠"写了也能还原"。

#### 2.5.1 行业做法：两半，缺一不可

| 半边 | 做法 | 代表 |
|---|---|---|
| **三态权限闸** | `allow` / `ask` / `deny`，deny 优先级最高 | **Claude Code `permissions`**（`allow`/`ask`/`deny` + 规则模式如 `Edit(/src/**)`） |
| **可逆性** | 每次改动自动进 git，一条命令回滚 | **Aider**（每次 AI 改动自动 commit + `/undo`）、**Cursor checkpoints**、Claude Code `/rewind` |

**你的 git 分支要求属于第二半，而且是主流答案。** 三态审批属于第一半，你提的三态和 Claude Code 的 `allow`/`ask`/`deny` 一模一样。

#### 2.5.2 安全员：确定性策略为主，模型只能"收紧"

> ⚠️ **安全员不是第三个角色。** 它是**一个审批插件**（挂在 `approval/request` 瀑布上），
> 复用 MiniCPM5-2B 但**独立调用、不参与对话**，你在界面上看到的只是审批提示。
> 全项目仍是 **两个角色、两个模型**（`07-技术方案.md` §3）。

> **核心原则：模型永远不能放松判定，只能收紧。**
> 即使模型被忽悠，最坏结果是"多问你一次"，而不是"放行了一个危险写入"。

```
approval/request 瀑布：
  [安全员 listener]  确定性策略（毫秒）+ 模型语义复核（仅灰区，~8s）
      ├─ 明确安全 → allowed-once        【通过】
      ├─ 明确危险 → rejected            【拒绝】
      └─ 灰区     → next() → [人类 UI answerer]  【需要人类批准】
```

**这是 DSH 原生扩展点，不是外挂。** `@deepseek-ai/dsh-user-approval` 的判定词汇（源码 `types.d.ts`）：

```ts
export type ApprovalOutcome = 'allowed-once' | 'rejected' | 'cancelled' | 'unavailable';
'approval/request'(this: Scoped<Agent>, req: ApprovalRequestEvent, next: () => Promise<ApprovalOutcome>): Promise<ApprovalOutcome>;
```

| 你的三态 | 实现 |
|---|---|
| 【通过】 | return `'allowed-once'`（**唯一的授权值**） |
| 【需要人类批准】 | `return next()` → 委托给人类 UI answerer |
| 【拒绝】 | return `'rejected'` |
| 模型返回非法值 | 被**规范化成 `'unavailable'`**（fail-closed 安全网） |

副产品：**每次请求与结果自动记入 session 审计日志**（源码："Every request and outcome is recorded in the requesting session's audit log"）。
且 `next()` 语义明确："a deployment composes **one terminal answerer**"——人类 UI 就是那个 terminal。

#### 2.5.3 确定性策略表（毫秒级，负责绝大多数判定）

| 情况 | 判定 |
|---|---|
| 写 workspace 内的 harness 自身文件（队列/配置/日志） | 【通过】（队列本身事件溯源，可重建） |
| 写 lab 内 **tracked** 文件 **且** 当前分支是 `research/*` | 【通过】 |
| 写 lab 内 tracked 文件 **但** 当前分支是 `codex/experiments` 或 detached HEAD | **【拒绝】**——不满足"必须先开分支" |
| **删除或覆盖** lab 内**未跟踪**文件（git 救不回） | 【需要人类批准】 |
| 新建文件 | 【通过】（无可失去） |
| 碰 `.venv/` / `models/` / `data/` | **【拒绝】** |
| 改 `tests/` 或 `configs/` 里的阈值（防"改测试让它过"） | 【需要人类批准】 |
| 单文件 > 512 KB，或单次 diff > 300 行 | 【需要人类批准】 |
| 二进制文件写入 | 【需要人类批准】 |
| 调用 `lab-run` 白名单外的入口 | **【拒绝】** |

**模型层只在灰区被调用**，输入是「任务描述 + 截断的 diff」，输出 `{"verdict":"normal|suspicious","reason":"…"}`。
`suspicious` → 升格为【需要人类批准】；`normal` → **不改变**确定性层的判定。

#### 2.5.4 模型选型：复用 MiniCPM5-2B，不引入"网安特调模型"

**你记的那类模型是错的工具**（诚实标注：web search 本次被限流，以下是既有知识，未联网复核）：

| 类别 | 代表 | 实际用途 | 适配？ |
|---|---|---|---|
| **网安特化** | WhiteRabbitNeo、Foundation-Sec、VulnLLM、CodeLlama | **漏洞挖掘 / 渗透测试**，输出漏洞报告 | ❌ **不是审批**——你的记忆正确 |
| **内容护栏分类器** | Llama Guard、ShieldGemma、Granite Guardian、Prompt Guard | **内容安全**分类（暴力/仇恨/越狱/PII） | ❌ taxonomy 是内容风险，不是"这次写入可不可逆" |
| **代码特调** | Qwen-Coder、DeepSeek-Coder、Granite Code | **读懂 diff** | ⚠️ 能力最接近，但没有"审批"对齐 |

**结论：没有任何现成模型是为"写入审批"训练的。** 把最终放行权交给模型是反模式——**审批器本身可被绕过**。

**因此选 MiniCPM5-2B**，理由：
1. 已常驻，**零边际成本、零额外下载**（符合"不要太复杂"）
2. 它只需做 `normal|suspicious` 二分类 + 理由，**比工具调用简单得多**（工具调用它 4/6，但这是更窄的任务）
3. 延迟只在灰区支付——确定性层毫秒级通过
4. 弱点被"只能收紧"完全兜住
5. 独立调用、独立提示，与值班员**不共享上下文**，不存在实质自审冲突

> 备选 Qwen3-8B（工具调用 6/6，更强）——**不推荐**：要额外常驻内存，且属 GPU 路径。

#### 2.5.5 ⚠️ 威胁模型（按你的假设设定）

你说"假设我不会攻击自己的机器" → **防误伤（bug/幻觉），不防对抗**。所以不需要对抗鲁棒性。
三道防线按成本排序：**可逆性（git）→ 影响范围（路径策略）→ 人工闸门**。这不是理论风险：
文件围栏只管"模型直接写文件"，管不了"模型写了个脚本、再由非受限进程执行它"——**git 才是兜住这一条的那层**。

### 2.6 Git 基线：三步 + 一个会让你白干几天的陷阱

#### 实测现状

| 项 | 值 |
|---|---|
| 分支 | `codex/experiments`（**唯一分支**） |
| HEAD | `7451cb1` |
| tag | **无** |
| remote | **无** |
| 工作区 | **tracked 文件零修改**；284 个全是未跟踪（3.60 GiB） |
| `.git` | 218 MB |

#### 三步（第 1、2 步不可跳过）

```bash
# 1. 给 codex 的原始 commit 一个不可变引用
git tag -a baseline/codex-delivery -m "codex 交付原始状态" 7451cb1

# 2. ⚠️ git 只保护 tracked 内容——这 284 个文件现在才进入保护范围
git checkout -b baseline/artifacts
git add -A && git commit -m "提交 codex 未跟踪 artifact（284 个）"

# 3. 研究员的工作分支（此后所有改动都在这里）
```

**codex 还原** = `git checkout codex/experiments`（或 `baseline/codex-delivery` tag）。
`codex/experiments` 分支引用**全程不被移动**。

#### ⚠️ 保护边界：`.gitignore` 划出了一块 git 永远救不回来的地

| `evidence/` | 1240 | 123 | 225M | ⚠️ 部分 |
| **`models/`** | **0** | 0 | **6.2G** | ❌ **被 ignore，永久在保护外** |

**两个后果**：

1. **第 2 步的 `git add -A` 只会收进那 284 个未忽略文件**（主要是 `evidence/` 与 `results/`），
   **不会**把 6.2G 的 `models/` 拖进仓库——**这是对的**，本来也不该进。
2. **`data/` / `models/` / `.venv/` 靠 git 救不回来。**
   所以 §2.5.3 里"碰这三个目录 → 【拒绝】"**不是保守，是必需**——
   这几个目录一旦被写坏，git 兜不住，只能重新下载 / 重建。

#### ⚠️ 陷阱：不能用 `git worktree`（会让研究循环静默失效）

实测 lab venv 中存在：

```
.venv/lib/python3.11/site-packages/__editable__.rlvr_l40s_lab-0.1.0.pth
  内容：/root/siton-tmp/rlvr-l40s-lab/src
```

且 `.venv/bin/python -c "import rlvr_lab"` → `/root/siton-tmp/rlvr-l40s-lab/src/rlvr_lab/__init__.py`。

**editable 安装永远指向原目录**——`git worktree` 里改的代码**不会被 import**，
研究循环会"改了但没生效"地静默失效，可能白烧几天机时。
→ **必须在原地开分支。**（除非同时设 `PYTHONPATH=<worktree>/src` 覆盖，
但那是多一个会错的零件，与"不要太复杂"冲突。）

## 5. 测试计划（行业通行分层）

LLM 系统与常规软件的关键差别：**确定性部分用断言，非确定性部分只能评测。**

### L1 · 确定性内核 —— 真单元测试，是闸门

| 测什么 | 怎么测 |
|---|---|
| 队列 append-only 语义 | 追加事件后 `current.json` 可**从 `events.jsonl` 重建**且逐字节相同 |
| 锁与原子性 | 并发认领同一请求，**有且仅有一个成功**；同目录 `rename` |
| 崩溃恢复 | 任意步骤 `kill -9`，重启后状态自洽、无重复投递 |
| 工具契约 | 每个工具的输入输出 schema |
| **`lab-run` 参数校验** | 拒绝任何不在白名单的入口与参数（**这是替代 bash 沙箱的那道闸**） |
| 文件围栏 | 尝试写 workspace 之外 → 必须得到 `FS_SANDBOX_DENIED` |

👉 **这层必须 100% 通过才允许进入下一阶段，没有阈值可谈。**

### L2 · 工具调用 —— fixture 评测，度量是 `pass^k` 而非 `pass@k`

固定 prompt → 期望的工具名 + 参数。参数用**结构匹配**（JSON/AST 精确比对），不比对自由文本。

**关键**：agent 要的是**一致性**，不是平均分。用 τ-bench 提出的 **`pass^k`——k 次全部通过才算过**。

现状：已有 6 用例雏形（MiniCPM5-2B 4/6），**要扩到覆盖 §4 契约表每一行**。

### L3 · 端到端场景 —— 脚本化 + 语义化 golden diff

把 §4 的对话录成脚本跑一遍。**绝不做字符串 diff**（措辞每次不同），比对**结构性事实**：
调了哪个工具、有没有真的产出 PNG、状态有没有真变。

> ⚠️ **temperature=0 也不保证可复现**（llama.cpp 的 batch / 线程调度有差异）。
> 所以 L2/L3 必然有一定 flaky。处理：k 取小（3~5），失败必须能定位到"模型问题还是代码问题"。

### L4 · 人验收 —— 你按 §4 逐行走

### 5.1 我不会做的事

- ❌ 不测"它聪明不聪明"——只测"在列举的 N 个场景里对不对"
- ❌ 不用未固定的采样参数做断言
- ❌ 不把 L2/L3 的分数当 gate（它们是**度量**，gate 是 L1 + 你的 L4）
