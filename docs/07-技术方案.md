## 2. 硬件与硬约束

| 项 | 实测值 | 影响 |
|---|---|---|
| GPU | L40S 48GB（可用 47.5 GiB） | 研究员与训练互斥 |
| CPU | 2× Xeon 8352V，**144 线程 / 2 NUMA 节点** | 线程数必须显式设定 |
| ISA | AVX512 + **VNNI**，**无 AMX** | Q8_0 不划算；INT4 是正解 |
| 内存 | 502 GB | 可放多模型 |
| 宿主 glibc | **2.27** | 大量现代组件需 PRoot 绕行 |
| 内核 / 沙箱 | **5.10 无 Landlock（ENOSYS）、无 bwrap、seccomp 禁 userns** | **bash 无法沙箱化**，见 §2.2 |
| 磁盘 | `/` 25G 空闲、`siton-tmp` 18G | 需谨慎管理 |

### 2.1 四条从实测得出的硬规则

1. **线程数必须显式指定**。llama.cpp 默认用满 144，实测 **tg 掉到 0.00（完全瘫痪）**。8B 用 16、2B 用 12。
2. **研究员与 RL 训练互斥**。训练峰值 46.9 GiB，L40S 只有 47.5 GiB。
3. **不动实验室 venv**（`/root/siton-tmp/rlvr-l40s-lab/.venv`）。需要新包一律新建 venv，用 `PYTHONPATH` 只读共享 torch。
4. **不给任何角色 bash 工具**。见 §2.2。

### 2.2 沙箱边界：文件层可用，shell 层不可用

| 层 | 机制 | 本机可用性 |
|---|---|---|
| **文件（读/写/编辑）** | `dsh-fs-sandbox`——**进程内路径判定**，`inject = ["sandboxPolicy"]`，不依赖任何 runner | ✅ **可用**：读不受限（lab 可读）、写限于 workspace + 平台临时区 |
| **shell（bash）** | `dsh-sandbox-local`——Linux runner 链 `["bwrap", "landlock"]`，`confine()` 对每个 mode 都包装，**无 mode 级旁路** | ❌ **不可用**：两者都探测失败 → 抛 `SANDBOX_UNAVAILABLE`（fail-closed） |

实测证据（`L40S-1-gpu`）：`which bwrap` 无；内核 `5.10.0-136.12.0.86.oe2203sp1`；
`landlock_create_ruleset(VERSION)` → `errno 38 ENOSYS`；`unshare --user` → `Operation not permitted`；
`/proc/self/status` 显示 `Seccomp: 2`。

> DSH 源码自述的 fallback：`Install bubblewrap or run a Landlock-enforcing kernel (Linux) …
> otherwise switch the consumer to danger-full-access.`

**因此**：值班员与研究员都**不挂 bash 工具**；实验执行走**专用工具 `lab-run`**——
模型选配置、我校验参数、由我的代码拉起 lab 里**预审入口**。模型全程不接触任意 shell。
这是 `07` "窄契约、幂等、可验证"原则的自然延伸，也顺带成为**替代 bash 沙箱的那道闸**。

**代价（必须诚实标注）**：文件层围栏是 **containment，不是 security boundary**。
它管得住"模型直接写文件"，管不住"模型写了个脚本、再由非受限进程执行它"——
这正是 `08-验收与交付计划.md` §2.5 那个待你拍板的开放项。

## 3. 两个角色

```
              ┌─────────────────────────────────────────────────────┐
机器事件 ────►│ 第一层 · CPU 常驻 · MiniCPM5-2B (IQ4_XS · 12 线程)   │
用户请求 ────►│                                                     │
              │  ├─ 【值班员】盯事件 · 记流水 · 查表                 │
              │  │             · 确定性操作（不依赖模型判断）        │
              └───────────────────┬─────────────────────────────────┘
                                  │ 需要规划 / 研究 / 写代码
                                  ▼
                    ┌───────────────────────────────────────┐
                    │ 第二层 · GPU · Qwen3-32B               │
                    │ 【研究员】设计 · 研究 · 写代码          │
                    │ ⚠ 仅实验间隙可装载（与训练互斥）        │
                    └───────────────┬───────────────────────┘
                                    │ GPU 被实验占用时
                                    ▼
                    requests/ 持久化队列
                    值班员回：原因 + ETA + 你有哪些选项
```

**两个角色的切换不是换模型，而是换 agent 预设**（提示 + 工具集）——同一个 llama-server 端点。

### 3.1 分工判据：可靠 vs 智力

**「可靠」是工具的属性，不是模型的属性。**

| | 值班员 | 研究员 |
|---|---|---|
| 操作性质 | 确定性、可验证 | 需理解与判断 | 需长程推理 |
| 例子 | 查状态、列缺口、**中止实验**、tail、队列 CRUD | 摘要日志、解读指标、决定画什么图 | 读任务书、设计方案、写代码 |
| 保障 | 窄工具契约 + 确认 + 校验 | 模型能力 | 模型能力 |

### 3.2 值班员的工具集（窄契约、幂等、可验证）

| 工具 | 契约 | 验证 |
|---|---|---|
| `lab-run-status <id>` | 读 `job.json` + metrics 尾部 → JSON | 字段存在 |

| `lab-gap` | 对比 `matrix.json` 与 `results/` | 集合差 |

## 4. 推理栈配置（实测最优）

### 4.1 为什么不用 Ollama

| 问题 | llama-server | Ollama |
|---|---|---|
| 思考通道 | CoT 直接在 `content`（实测 `rsn_chars=0`） | 拆到 `reasoning`，`content` 为空 |
| PRoot 稳定性 | 稳定 | **GPU watchdog 超时并崩溃** |
| 预填充 | 更快 | 较慢 |
| 参数控制 | 全部暴露 | 受限 |

### 4.2 MiniCPM5-2B 最优配置（实测）

| 指标 | 值 |
|---|---|
| pp512 | **290.3 t/s** |
| tg128 | **37.9 t/s** |
| 读 2k token 日志 | 6.9 s |
| 写 100 token 摘要 | 2.6 s |
| **端到端任务** | **约 9.5 s** |

| 量化 | 大小 | t=16 pp | t=16 tg | 判定 |

### 4.3 研究员模型：为什么是通用模型、为什么是 32B

**结论：保持 Qwen3-32B（通用推理模型，Q4_K_M）。不引入编码特调，也不引入"AI4AI 特调"——后者不存在。**

#### 证据：MLE-bench 榜首全是通用模型

[MLE-bench](https://github.com/openai/mle-bench)（OpenAI，75 个 Kaggle 竞赛，评"AI 做 ML 工程"的能力）
是离"AI4AI"最近的公开评测。2026-03 榜单前列：

| Agent 脚手架 | 所用模型 | All (%) |
|---|---|---:|
| Famou-Agent 2.0 | **Gemini-3-Pro-Preview** | 64.44 |
| AIBuildAI | **Claude-Opus-4.6** | 63.11 |
| CAIR MARS+ | **Gemini-3-Pro-Preview** | 62.67 |
| ML-Master 2.0 | **Deepseek-V3.2-Speciale** | 56.44 |
| Thesis | gpt-5-codex | 48.44 |
| R&D-Agent | **gpt-5** | 35.11 |
| AIDE | llama-3.1-405b-instruct | 3.33 |

**没有一个条目使用"网安特调"或"AI4AI 特调"模型。** 姊妹基准 **MLGym**（Meta）同理。
这个领域的产物是**脚手架**（AIDE / R&D-Agent / ML-Master / Famou-Agent / MLEvolve / CAIR MARS），不是特调模型。

#### 决定性观察：脚手架 > 通用/特调之分

同一个 **Gemini-2.5-Pro**，换脚手架：

| 脚手架 | All (%) |
|---|---:|
| Famou-Agent 2.0 | **59.56** |
| Famou-Agent | 43.56 |
| CAIR MLE-STAR-Pro-1.0 | 38.67 |

**同模型、跨脚手架差 21 个百分点。** 而"通用 vs 编码特调"的证据是混杂的
（gpt-5-codex 48.44% 反而高于 gpt-5 的 35.11%，但脚手架不同，不是干净对照）。

**三个杠杆的排序：模型档位 ≫ 脚手架 > 通用/特调之分。**
→ 纠结"通用 vs 编码特调"是**在最小的那个杠杆上花力气**。

#### 为什么不是 Qwen3-30B-A3B

Qwen3 技术报告（arXiv 2505.09388）原文：30B-A3B
"achieves **comparable performance to Qwen3-14B-Base** and Qwen2.5-32B-Base"。
→ 它是 **14B 档位的质量 + MoE 的速度**，**不是 32B 的替代品**。

且本项目的瓶颈**不是延迟**——一次正式 run 就是 4.7 小时，解码速度差别被完全淹没。
→ **质量优先于速度 → 选 dense 32B。**

#### 为什么"数学特调"也不对

RLVR 训练的**学生**（数学/推理小模型）才是"数学特调"。
研究员是**跑训练的人**，不是被训练的对象。**数学特调模型是研究对象，不是研究员。**

#### 诚实的期望设定

榜单上 48–80% 全是前沿闭源模型；开源最好成绩（405B + AIDE）只有 **3.33%**。
我们的 32B Q4 远低于榜单任何条目。但**任务难度不可比**——MLE-bench 是"从零解 Kaggle 竞赛"，
我们的 P0 是"在已有且脚手架完备的代码库上续跑 + 一个开放研究问题"。P0 六项中：

| 类别 | 项 |
|---|---|
| **执行**（32B 够用） | 速记法 SFT→GRPO ×2、补 24 个审计点、三张主图 ×2、提交 284 artifact、GitHub 分支+报告 |
| **研究**（可能失败，**用户已批准允许负结果**） | 解决速记法数据生成退化 |

→ **模型选型不是本项目的成败关键，脚手架才是。**

#### ⚠️ 但发现一个更紧急的问题：研究员**目前没有推理路径**

实测（2026-09-11）：

| 项 | 状态 |
|---|---|
| CUDA 构建的 `llama-server` | ❌ **不存在**（只有 `build-cpu`，`--version` 报 `cpu`） |
| vLLM / sglang / llama_cpp | ❌ 全无 |
| transformers / torch | ✅ 4.57.1 / 2.6.0+cu124，`torch.cuda.is_available()=True` |
| flash-attn | ❌ 无 |
| 服务器上的模型 | ❌ **最大只有 Qwen3-8B**，**没有任何 32B 模型** |
| GPU | ✅ L40S 空闲（0 MiB 占用） |

→ **"研究员 = Qwen3-32B"目前是纸面配置。** 要落地必须先解决三件事：
① 下载模型（~20 GB）② 推理栈（修 llama.cpp CUDA 构建 / 新建 vLLM venv / 用 transformers）
③ 磁盘（`/` 仅剩 25 G）。

## 6. 绘图：三层工具，不执行模型生成的代码

### 6.1 实测：MiniCPM5-2B 会不会写 matplotlib

**会。** 实测（CPU llama-server，IQ4_XS，12 线程）：

| 测试 | 结果 | 输出 token | 耗时 |
|---|---|---:|---:|
| **裸写 matplotlib 代码** | **执行成功、产出 PNG**；`set_title/set_xlabel/set_ylabel/grid/legend` 各 4 个，数据从正确文件读取，一次通过 | 823 | 25.6 s |
| **工具 `plot_metrics(run_id, kinds)`** | 参数完全正确：`{"run_id":"gsm8k-grpo-formal-001","kinds":["learning","stability"]}` | **220** | **7.7 s** |
| **工具 `plot_series(source,x,y,output)`** | 参数完全正确：`{"source":"metrics","x":"step","y":["kl","loss"],"output":"explore.png"}` | 899 | 28.8 s |

唯一瑕疵：`set_xticks(steps)` 在 64 个 step 上画出 64 个刻度——**可用但难看**，属审美问题，不是正确性问题。

### 6.2 那为什么还要工具化

**决定性理由不是成本，是安全边界**：

| | 裸写代码 | 工具调用 |
|---|---|---|
| 输出 token | 823 | **220** |
| 耗时 | 25.6 s | **7.7 s** |
| **是否执行模型生成的代码** | ⚠️ **是** | **否** |
| 与 codex 交付图一致 | 风格会漂移 | **完全相同**（同一份代码） |

执行 LLM 生成的代码需要沙箱，而**这台机器上沙箱受限**（`unshare` 被禁，无 bwrap / nsjail / docker）。
工具化完全不碰这条路径。

**并且不需要 skill 文档**——skill 是"教它怎么写"，而它本来就会写；工具是"让它不必写"。

### 6.3 三层绘图工具

```
plot_metrics(run_id, kinds)        → 调 rlvr_lab.plot.render()
   覆盖 7 组固定诊断图：learning / stability / generation /
   resources / acceptance / tokens / system_resources

plot_strategy_curves(project)      → 调 rlvr_lab.strategy_curves.plot()
   出三张主图：strategy_singlepoint / budget_jumps / actual_cost
   这是交付物，必须与 codex 的图完全一致

plot_series(source, x, y, output)  → 薄封装通用折线
   source ∈ {metrics, groups, validation}
   只覆盖 lab 硬编码面板没有的探索性视角
```

**原则**：标准图走**已验证代码**（保证与交付物一致），探索图走**薄封装**，两者都**不执行模型生成的代码**。
模型只负责选 `kind` 与填参数——这正是它 R1 5/5 擅长的事。

### 6.4 lab 现有绘图能力的一个限制

codex 的绘图模块是**固定报表生成器**，不是通用绘图工具：`plot.py`（565 行）从固定的 run 目录结构读
`metrics.jsonl` / `groups.jsonl` / `validation.jsonl`，渲染 7 组硬编码面板；另有 `strategy_curves.py`
出三张策略图。合计 39 PNG + 39 SVG，1444 行代码。

**它没有"画 X vs Y"的自由度**——这正是第三层 `plot_series` 要补的位置。

## 7. 请求队列

### 7.1 形态：一个普通目录（权威真相）

```
requests/
  events.jsonl      # 只追加：created/edited/cancelled/reprioritised/claimed/completed
  current.json      # 派生视图（可重建）
  <id>.json         # 当前状态 + revision history
```

三个性质：用户可**直接编辑**（ssh/vscode）、值班员改同一批文件（不需唤醒）、重启不丢且可审计。

### 7.2 值班员独立支持的操作

| 用户说 | 操作 | 允许 status |
|---|---|---|
| "队列里有什么" | list | 随时 |
| "第 2 条改成…" | edit | `queued` |
| "提到最前" | reprioritise | `queued` |
| "改成不需要研究员" | retarget tier | `queued` |
| "删了第 2 条" | cancel | `queued` |

### 7.3 不可静默删除的边界

```
queued ──claim──► claimed ──► in_progress ──► done
  │                  │
  │                  └─ 用户不能删，只能：① 追加修正 ② 叫停
  └─ 可随时 edit / cancel / reprioritise
```

并发安全：编辑与认领都先取 `requests/.lock`；认领用**同目录 rename**（原子）。

### 7.4 前端

`@linxin666/dsh-client-ui-task-board`（npm 0.3.20，要求 `dsh >= 0.1.5-rc.1`，**本机正好满足**）。
装法：`dsh plugin --profile web add @linxin666/dsh-client-ui-task-board@latest`

**它不实现排队**，只做可视化与执行——排队真相仍在 `requests/`。
**两个需知风险**：① 每 UTC 日向 `dsh-market.com` 发匿名心跳；② 社区包。
**容器内限制**：电源保护需 systemd-logind（本容器显示 `unsupported`，无妨）；账本有单进程锁，不可同时起两个 DSH。
