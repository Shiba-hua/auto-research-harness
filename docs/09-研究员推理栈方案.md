## 2. 继承方式：**不改 codex 的任何东西**

### 2.1 codex 的启动器长这样（原文）

```bash
exec "$RLVR_VLLM_RUNTIME_ROOT/bin/proot" -0 -r "$RLVR_VLLM_RUNTIME_ROOT/rootfs" \
  -b "$RLVR_VLLM_RUNTIME_ROOT/rootfs:$RLVR_VLLM_RUNTIME_ROOT/rootfs" \
  -b /dev -b /proc -b /sys -b /etc/resolv.conf -b /etc/hosts \
  -b "$RLVR_LAB_ROOT:/workspace" -b "$RLVR_BASE_PREFIX:$RLVR_BASE_PREFIX" \
  -b "$RLVR_VLLM_RUNTIME_ROOT/evidence:/run-evidence" \
  -b "$RLVR_VLLM_RUNTIME_ROOT/cache:/run-cache" \
  -b "$RLVR_VLLM_RUNTIME_ROOT/wheelhouse:/wheelhouse" -w /workspace \
  /usr/bin/env -i PATH=/opt/rlvr-vllm-venv/bin:... \
  LD_LIBRARY_PATH=/opt/nvidia-driver ... \
  PYTHONPATH=/workspace/src PYTHONDONTWRITEBYTECODE=1 ...
```

**这个启动器做对了几件关键的事**，值得保留：

| 设计 | 意义 |
|---|---|
| Ubuntu 22.04 rootfs（**glibc 2.35**） | 绕开宿主 glibc 2.27 —— 这就是 `GLIBC_2.28 not found` 的解法 |
| `LD_LIBRARY_PATH=/opt/nvidia-driver` | 注入宿主驱动库，**不需要在 guest 里装驱动** |
| `-b $RLVR_LAB_ROOT:/workspace` + `-w /workspace` | lab 在 guest 里就是 `/workspace` |
| `PYTHONPATH=/workspace/src` | guest 里直接 `import rlvr_lab` |
| `env -i`（清空环境） | 不会从宿主漏进脏变量 |
| `PIP_CONFIG_FILE=/dev/null` `PIP_REQUIRE_VIRTUALENV=1` | 防止往错误的地方装包 |
| `HF_HOME=/run-cache/huggingface` 等 5 个 cache 重定向 | 缓存全落在 userspace 内，不污染宿主 |

### 2.2 存储：`/root/siton-pub` 是只读的，模型只能放 `/dev/shm`

实测各挂载点的**可写性**（`touch` 探测，不是看 `df`）：

| 路径 | 空闲 | 可写 | 持久 | 备注 |
|---|---:|---|---|---|
| `/root/siton-pub` | 613G | ❌ **只读** | — | 平台**刻意** `ro` 挂载（`mount` 选项里明确 `ro`）——**看着大，用不了** |
| **`/dev/shm`** | **45G** | ✅ | ❌ **重启即失** | tmpfs，RAM 后备（总内存 502G） |
| `/root/siton-data-f5efa…` | 29G | ✅ | ✅ | NFS v4.2，网络盘 |
| `/`（overlay） | 25G | ✅ | ✅ | Docker overlay |
| `/root/siton-tmp` | 18G | ✅ | ✅ | lab 所在盘；已很紧 |

**结论（已获你确认）**：模型落 **`/dev/shm/models`**。
45G 足够 **FP8 的 ~32 GB**，所以 **§3 的"FP8 优先"路线保住了**；
若走 4-bit（~19 GB）则位置更宽裕。

> ⚠️ **代价必须记住**：`/dev/shm` 是 tmpfs，**宿主重启后模型消失，需要重新下载**。
> 这是用"重新下载一次"换"质量优先 + 不占用紧张的系统盘"，是一笔划算的交换
> （对照：把 32G 塞进只剩 25G 的 `/` 会让容器本身变危险）。

### 2.3 我要加的：一个**自己的 wrapper**，不修改 codex 的

```bash
# /root/dsh-harness/bin/vllm-run      ← 我写的，与 codex 的并存
exec "$RLVR_VLLM_RUNTIME_ROOT/bin/proot" -0 -r "$RLVR_VLLM_RUNTIME_ROOT/rootfs" \
     …（与 codex 的 bind 列表逐字相同）… \
     -b /dev/shm/models:/models        # ← 只加这一行
     "$@"
```

**已验证**：`/models` 在 guest 内可访问，`/dev/shm` 在 guest 内可写。
`codex launcher sha256 = 614fa702bd483cbff7e707a26db5a7607efe5152c406b4c573be4d5bfebeb4e1`
（记下来，用于发现 codex 侧改动导致的漂移）。

**原则**：codex 的 `bin/run` 与 venv **一律不动**。这是 `05-环境部署现状.md` §3.0 硬规则的延伸。

## 3. 模型选型

### 3.1 硬约束

| 约束 | 值 |
|---|---|
| 显存 | L40S **47.5 GiB** 可用（`memory.total = 49140 MiB`） |
| 算力 | sm_89（Ada）→ **原生支持 FP8** |
| 与训练互斥 | 训练峰值 **46.9 GiB** → 研究员与训练**不能共存**（`07` §2.1 规则 2） |
| 磁盘 | 模型落 **`/dev/shm/models`**（45G，**重启即失**）；`/root/siton-pub` 是**只读**的 |

### 3.2 KV cache 账（Qwen3-32B：64 层 / 8 KV heads / head_dim 128）

```
每 token = 2(K,V) × 64 层 × 8 heads × 128 dim × 2 B = 262,144 B = 0.25 MiB
40,960 token 上下文 → 10,240 MiB = 10.0 GiB
```

| 方案 | 权重 | KV@40k | 开销 | 合计 | 47.5 GiB 内？ |
|---|---:|---:|---:|---:|---|
| **FP8**（1 B/参数） | ~30.5 GiB | 10.0 | ~4 | **~44.5 GiB** | ⚠️ 能放，但很紧 |
| **AWQ / GPTQ Int4** | ~18.5 GiB | 10.0 | ~4 | **~32.5 GiB** | ✅ 宽裕 |

### 3.3 决定：**`Qwen/Qwen3-32B-AWQ`（4bit）** —— 按你的规则推出来的，不是默认

你的 4 号意见给的是程序：**优先 8bit 现成量化；若官方/社区有现成 4bit 且"不会明显降智 + 真的能搞定那么长的上下文"，则用 4bit。** 逐步执行：

#### 步骤 1 · 现成量化存不存在 → **两者都存在，且都是官方的**

| | 仓库 | 下载量 | 权重大小 |
|---|---|---:|---:|
| 8bit | **`Qwen/Qwen3-32B-FP8`** | 173,177 | 31.97 GiB |
| 4bit | **`Qwen/Qwen3-32B-AWQ`** | **697,902** | **18.00 GiB** |

（社区备选：`RedHatAI/Qwen3-32B-quantized.w4a16` 8.8k、`unsloth/Qwen3-32B-bnb-4bit` 74k、`JunHowie/Qwen3-32B-GPTQ-Int4` 2.0k。官方 AWQ 下载量最高。）

#### 步骤 2 · 门槛 (a)「不会明显降智」→ ✅ **通过**

`Qwen/Qwen3-32B-AWQ` 模型卡**自带**官方对比表：

| 模式 | 量化 | LiveBench 2024-11-25 | GPQA | MMLU-Redux | AIME24 |
|---|---|---:|---:|---:|---:|
| Thinking | bf16 | 74.9 | 68.4 | 90.9 | 81.4 |
| Thinking | **AWQ-int4** | 73.1 | **69.0** | 90.8 | 79.4 |
| | **差** | **−1.8** | **+0.6** | **−0.1** | **−2.0** |
| Non-Thinking | bf16 | 59.8 | 54.6 | 85.7 | — |
| Non-Thinking | **AWQ-int4** | **59.8** | 53.1 | 85.6 | — |

**平均损失约 1%，GPQA 反超。** 对照基准：Qwen3 技术报告（arXiv 2505.09388）明确 30B-A3B
"achieves comparable performance to **Qwen3-14B-Base**"——它是 **14B 档**。
32B-AWQ 掉 1% 之后仍**远强于 30B-A3B**。✅

#### 步骤 3 · 门槛 (b)「真的能搞定那么长的上下文」→ ⚠️ **FP8 反而不通过**

`max_position_embeddings = 40960`（**官方默认**，不是我们硬拉的）。

```
KV 每 token = 2(K,V) × 64 层 × 8 KV heads × 128 head_dim × 2 B = 0.25 MiB
@ 40,960 token → 10.0 GiB
```

| 方案 | 权重 | +KV@40k | +开销 | 合计 | 47.5 GiB 内 |
|---|---:|---:|---:|---:|---|
| FP8 | 31.97 | 10.0 | ~3–4 | **~45–46** | ⚠️ **贴边，实测很可能 OOM** |
| **AWQ** | **18.00** | 10.0 | ~3–4 | **~31–32** | ✅ **余 ~15 GiB** |

**8bit 在这一条上是"更危险"而不是"更保险"**：权重比 4bit 大一倍，40k 上下文下顶到 45–46/47.5 GiB。

#### 步骤 4 · 结论

**4bit 的两个门槛都通过，而 8bit 在第 (b) 条上失败 → 触发你写的"则用 4bit"。**

**下载 `Qwen/Qwen3-32B-AWQ`**（AWQ，`bits=4, group_size=128, version=gemm, zero_point=true`，vLLM 0.10.2 原生支持）。
额外好处：**下载量减半**（18 GiB vs 32 GiB），`/dev/shm` 的 45G 更宽裕。

**不做的事**：不做在线 FP8（本就要 BF16 中转，64 GiB 放不下，且我们不需要）；
不选 BF16（61 GiB）；不选 30B-A3B（14B 档）；不为了省 18G 磁盘而牺牲 40k 上下文。

### 3.4 ★ 附带发现：可能直接解释 P0 #1 的"速记法退化"

`Qwen/Qwen3-32B-AWQ` 模型卡里 Qwen 官方给了两条**强制**建议：

1. > For thinking mode, use `Temperature=0.6`, `TopP=0.95`, `TopK=20`, `MinP=0`.
   > **DO NOT use greedy decoding**, as it can lead to **performance degradation and endless repetitions**.
2. > **We strongly recommend setting `presence_penalty=1.5` for quantized models**
   > （用于减少无休止重复）

**这直接命中 P0 #1 的症状**：codex 记录的速记法退化是"8B 教师在 JSON 阶段 **token 循环**，
67,014/86,998 token 被循环覆盖"。**token 循环正是 repetitive degeneration**，
而官方说这**恰是贪心/低 temperature 的已知后果**，量化模型还额外需要 `presence_penalty`。

→ **这可能是一个配置问题，而不是模型能力问题。** 值得作为研究的第一条假设去验。

⚠️ 同时它**推翻了我 V8 的测试方法**：我用 `temperature=0` 测"确定性"，
但 Qwen3 thinking 模式**明确禁止贪心解码**。→ V8 必须改成官方采样参数重做，
且"确定性"这个目标本身对 Qwen3 thinking 就是错的（应当测**分布稳定性**而非逐字一致）。

## 5. GPU 仲裁：已实测，且**找到一个真 bug**

**事实**：训练峰值 46.9 GiB，卡只有 47.5 GiB → **研究员与训练互斥，没有折中**。

```
要跑实验 ──► 停 vLLM ──► 证明显存已释放（拿凭证）──► 起训练 ──► 跑完 ──► 起 vLLM
```

### 5.1 ⚠️ 实测发现：杀 PRoot 包装进程**不会**关掉 vLLM

这正是我原先标注的未验证项（codex 在 smoke 的 limitations 里写了
`"Process exit and released GPU resources must be verified separately."`），**实测确认它是真问题**：

| 动作 | 结果 |
|---|---|
| `kill -TERM <proot 包装进程 PID>` | ❌ **显存照旧 15770 MiB**；guest 的 vLLM 被**孤儿化到 PID 1**（`ps` 显示 `PPID=1`），**继续占着 15764 MiB** |
| `kill -TERM <guest 内 vllm serve 的 host PID>` | ✅ **15770 → 0 MiB 干净释放**，无残留进程 |

**根因**：PRoot 只是系统调用翻译层，它的子进程是**真实宿主进程**。
杀掉 PRoot 不传播信号给子进程——它们被 init 收养后继续活着。

**正确关闭规程**（已固化为脚本）：

```bash
# 1. 精确找 guest 的 vLLM 宿主 PID（[v] 防止 pgrep 匹配到自己 —— 我踩过这个坑，它会把会话杀掉）
PIDS=$(pgrep -f "[v]llm serve")
# 2. 直接给它 SIGTERM，让 vLLM 自己清理 CUDA context
kill -TERM $PIDS
# 3. 轮询直到显存回落
```

### 5.2 凭证规则：两个条件必须**同时**满足

```
发凭证 ⟺ gpu_used_mib < 1000  AND  leftover_pids == 0
```

**为什么不能只看显存**：存在"进程还活着但已不占显存"的中间态。
只看显存就发凭证，下一次训练启动时可能被这个残留进程干扰（抢占、CUDA 初始化竞态）。
**两个都满足才发凭证，否则拒绝启动训练**（fail-closed，与 DSH 沙箱同一哲学）。

**凭证不可伪造**：凭证内容包含 `nvidia-smi` 当次读数与残留进程计数；
值班员**只转发凭证、不做判断**——判断在脚本里，模型不参与（与 `07` 的 `lab-abort` 同构）。

### 6.1 V8 的意外结果（必须谨慎解读）

| 来源 | 条件 | 结果 |
|---|---|---|
| **我的实测** | vLLM server，`temperature=0`，**同一进程内连跑 5 次** | ✅ **5/5 完全一致**（同一 SHA256） |

**不矛盾，但结论要收窄**：`temperature=0` 在**同一个 server 进程内**是确定的；

### 6.2 V4 暴露的一个必须处理的细节：思维链吃光 token

V4 与 V8 的返回里，`content` **全部是 `<think>` 开头**，而 V8 的
`finish_reason` 是 **`length`** —— 24 个 token 全被思考块吃掉，**答案一个字没输出**。
同时 `reasoning_content: null`（思考没有独立字段，与 `06` §5.2 的 llama-server 结论一致）。

**对 harness 的直接影响**：
1. `max_tokens` 必须**给足**（思考 + 答案），否则会静默产出"只有思考没有结论"的回复；
2. 或者显式关思考（Qwen3 的 `enable_thinking: false` / `/no_think`），
   但研究员做研究诊断**需要**思考，所以倾向给足预算而非关闭；
3. **值班员的 ETA 提示（`07` §3.2）要按这个修正**——不能按"答案长度"估，要按"思考+答案"估。
