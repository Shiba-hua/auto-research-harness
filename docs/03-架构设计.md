# 03 · 架构设计：两个角色与可编辑请求队列

## 1. 两个角色

| 角色 | 模型 | 位置 | 常驻 | 职责 |
|---|---|---|---|---|
| **值班员** | **MiniCPM5-2B** · IQ4_XS · 12 线程 | CPU | ✅ 常驻 | 盯事件、记流水、查表、**执行确定性操作**、**摘要 / 解读 / 制图** |
| **研究员** | **Qwen3-32B** · Q4_K_M | GPU | ❌ 仅实验间隙 | 读任务书与仓库、设计方案、写代码 |

### 1.0 为什么是两个角色而不是三个

早期方案是**三个角色三个模型**（值班员 0.8B / 助理研究员 2–3B / 研究员 32B）。实测后合并为**两个**。

**合并第一层两个角色的依据**

| 模型 | R1 查表 | R2 三分类 | 输出 token | tg128 |
|---|---:|---:|---:|---:|
| Qwen3.5-0.8B | **0/5** ❌ | 1/3 | 1500（撞上限） | 51.6 |
| **MiniCPM5-2B** | **5/5** ✅ | **3/3** ✅ | **270** | 37.9 |

0.8B **答不出**"从 digest 提取 5 个数值"这类指令；2B 不仅 5/5，输出还简洁 5.5 倍。
**"助理研究员"这个角色被值班员吸收**——两者本来就跑在同一个模型上，把它们分成两个角色只是记账，不是分工。

**值班员与研究员不能合并的依据**

研究员需要 28.4 GiB 显存，而 RL 训练峰值 46.9 GiB，**两者无法共存**（整卡只有 47.5 GiB）。
所以研究员**必须按需装载**，与**常驻**的值班员天然分层——这是**资源**上的必然，不是记账上的选择。

### 1.1 命名说明

| 角色 | 配置名 | 命名理由 |
|---|---|---|
| **值班员** | `duty` | "值班"准确表达**唯一保证在场**这个本质——它不是最弱的，是永远有人的那个。它同时承担智力工作（摘要、解读、制图），所以**不是"低配版研究员"** |
| **研究员** | `researcher` | 方向把控与方案设计 |

> 曾用名"操作员""助理研究员"均已弃用——它们把第一层说低了，也人为制造了一个不存在的层级。

### 1.2 值班员的职责边界：可靠 vs 智力

**核心原则：「可靠」是工具的属性，不是模型的属性。**

只要操作是一个**窄契约、幂等、可验证**的确定性脚本（例如 `lab-abort <run_id>` → kill 进程组 → 等 release → 校验 `gpu-release.json` → 返回凭证），那么**连规则都能可靠地调用它**，不需要模型有多聪明。

值班员承担**两类**工作，用不同机制保障：

| 类别 | 例子 | 保障机制 |
|---|---|---|
| **确定性操作** | 查状态、列缺口、中止实验、tail 日志、队列 CRUD、查 GPU | **窄工具契约 + 确认 + 校验**，由规则/模式匹配选择工具，**不依赖模型的工具调用能力** |
| **智力操作** | 摘要日志、解读指标、制图 | **模型能力本身**（实测：R1 5/5、R2 3/3） |

**关键**：破坏性操作**永远走第一类**——实测 MiniCPM5-2B 在"中止实验"用例上返回空调用，但这**不是模型缺陷**，而是设计错误：这类操作本就不该交给任何规模的模型判断。

### 1.3 值班员的职责（哨兵 + 可靠操作 + 智力操作）

值班员**同时承担两类工作**。

#### 第一类：盯梢与分诊

- **盯**：`.pid` / `.exit` / `.finished` / `job.json` / `gpu-release.json` / 日志 mtime / GPU 利用率
- **记**：把事件写成流水账（供研究员回来后接手——这就是"期间发生了什么"的答案）
- **判**：这个事件要不要叫人？
  - 正常跑 → 不叫人
  - 正常结束 / 异常 → 走第二类（智力操作），由**值班员自己**解读
  - 规则判不了 → 做一次三分类

#### 第二类：智力操作

1. **摘要日志** —— 吃**确定性摘要**，不吃原文
2. **解读中间结果** —— 指标异常、失败原因、趋势判断
3. **制图** —— 决定画什么、选哪个脚本、传哪些参数

> 实测依据：MiniCPM5-2B 在 R1 查表 **5/5**、R2 三分类 **3/3**、R4-ETA **1/1**，输出仅 270 token。
> **这一类不"升级"到任何其他模型**——它就是值班员的正常工作。

#### 确定性工具集（窄契约、幂等、可验证）

| 工具 | 契约 | 验证方式 |
|---|---|---|
| `lab-run-status <run_id>` | 读 `job.json` + metrics 尾部 → JSON | 字段存在性 |
| `lab-run-list` | 扫 `results/` + `evidence/` | 计数一致 |
| `lab-gap` | 对比 `matrix.json` 与 `results/` | 集合差 |
| `lab-abort <run_id>` | kill 进程组 → 等 `release_timeout_seconds` → 校验 `gpu-release.json` | **返回释放凭证，无凭证即失败** |
| `lab-tail <run_id> [n]` | 日志尾部 | 行数 |
| `lab-gpu` | `nvidia-smi` 查询 | 解析成功 |
| `req-list/add/edit/cancel/reprioritise` | 队列 CRUD（事件溯源） | `events.jsonl` 追加成功 |
| `lab-estimate <run_id>` | 由 `started_unix + timeout_seconds` 算 ETA | 数值有效性 |

> **中止是安全敏感操作**：值班员识别意图 → 回显"将中止 X，代价 Y" → **等用户确认** → 执行。
> 执行本身纯确定性，**由规则/模式匹配选择工具，不依赖模型的工具调用能力**。

### 1.4 研究员的职责（第二层，独立模型）

- 读任务书与仓库（39 docs / 221 evidence / 121 results / 130 commits）
- 推断缺口、识别阻塞
- 设计方案（例如修速记法退化）
- 写代码、执行、验证、报告

> **只在实验间隙出现**（GPU 约束，见 §3）。值班员处理不了的请求进入 `requests/` 队列等它。

## 2. 双向单一入口

**值班员是机器事件与用户请求的共同入口（front door）。**

```
机器事件 ──┐
           ├──► 【值班员】MiniCPM5-2B · CPU 常驻
用户请求 ──┘         │
                     ├─ 能查表答的           → 自己答（秒级）
                     ├─ 确定性工具（中止等）  → 规则匹配 + 确认后执行
                     ├─ 要摘要 / 解读 / 制图  → 自己做（智力操作）
                     └─ 要规划 / 写代码       → 排队，唤【研究员】
```

**为什么必须是值班员当入口**：
1. 它是**唯一常驻**的组件——**第二层按需装载**，装载本身要时间（研究员需 30–60s 从磁盘读 18.4 GB）
2. 它**手上有状态**——一直在盯，知道"现在在跑什么、跑了多久"
3. 它是**唯一能保证一定回话**的组件。哪怕答案是"不行"，也得有人说出这句话

这对应行业模式：**SLM 默认入口 + 不确定性感知升级**。

## 3. GPU 争用：唯一的硬约束

| 项 | 显存 |
|---|---:|
| L40S 可用总量 | **47.5 GiB** |
| RL 训练峰值（实测 `arc-grpo-formal-001`） | **46.9 GiB** |
| 研究员 Qwen3-32B Q4_K_M @40k（权重+KV） | 28.4 GiB |

**28.4 + 46.9 = 75.3 GiB ≫ 47.5 GiB → 研究员与训练无法共存。**（换成 Qwen3-8B 的 10.3 GiB 同样放不下。）

**推论**：
- 实验串行，不存在并行
- 研究员的活动窗口 = 实验间隙
- 实验运行期间，前端由值班员（CPU）承担
- 一次装载可做大量推理，然后放手让实验跑几小时——这天然适合"长程目标"模式

**利用 CPU 削弱该约束**：这台机器有 2×Xeon 8352V / 144 线程 / 502GB RAM，CPU 推理是可行的第三选择（详见 `04-模型选型-待讨论.md`）。行业上 CPU 已重新成为一等公民的推理目标（Intel：agentic 部署下 CPU:GPU 比例从训练的 1:8 变成 1:1，某些场景 4:1）。

## 4. 请求队列：可编辑的一等公民

### 4.1 形态：一个普通目录（不是数据结构）

```
requests/
  events.jsonl      # 只追加：created / edited / cancelled / reprioritised / claimed / completed
  current.json      # 派生视图（缓存，可从 events.jsonl 重建）
  <id>.json         # 每条请求当前状态 + revision history
```

**三个性质**：
- 用户随时能**直接改**（ssh / vscode / scp），不必经过对话
- 值班员改同一批文件——**不需要被唤醒就能操作队列**
- 重启不丢，且可审计（改动不覆盖，记事件）

### 4.2 请求 schema

```json
{
  "id": "req-20260911T113000-ask-researcher",
  "source": "user",                  // user | system
  "tier": "researcher",              // duty | associate | researcher
  "status": "queued",                // queued | claimed | in_progress | done | cancelled
  "priority": 50,
  "body": "速记法为什么老是退化？读一下 v4 诊断，给我一个方案",
  "context": {"run_id": "...", "attachments": []},
  "deferred_reason": "gpu_busy",
  "eta": "2026-09-11T13:15:00Z",
  "revision": 3,
  "history": [
    {"rev": 1, "op": "created",       "at": "11:30"},
    {"rev": 2, "op": "edited",        "at": "11:31", "by": "user", "field": "body"},
    {"rev": 3, "op": "reprioritised", "at": "11:33", "from": 50, "to": 10}
  ]
}
```

### 4.3 值班员必须独立支持的操作（不依赖研究员）

| 用户说 | 操作 | 允许的 status |
|---|---|---|
| "队列里现在有什么" | list | 随时 |
| "第 2 条改成……" | edit body / context | `queued` |
| "把这条提到最前" | reprioritise | `queued` |
| "把这条改成不需要研究员" | retarget role | `queued` |
| "删了第 2 条" | cancel | `queued` |
| "全清掉" | cancel all | `queued` |

**这是关键**：值班员常驻，所以这些操作**永远可用**，不会出现"想删但没人能处理"的死结。

### 4.4 状态机与不可静默删除的边界

```
queued ──claim──► claimed ──► in_progress ──► done
  │                  │
  │                  └─ 用户不能删，只能：
  │                     ① 追加一条修正请求，或
  │                     ② 叫它停下（作为一条高优先级请求）
  │
  └─ 可随时 edit / cancel / reprioritise
```

**为什么**：研究员一旦开始读请求并动手，静默删除会造成"改了半截"的状态。正确做法是**追加修正**或**叫停**。

值班员必须能诚实地说：

> "这条已经被研究员取走了（领取于 11:32），删不掉。我可以帮你 ① 追加一条修正，或 ② 叫它停下来。"

### 4.5 并发安全

认领必须原子化，避免"用户正在编辑、研究员同时取走"的竞态：

```
编辑前   → acquire requests/.lock
认领前   → acquire requests/.lock
认领动作 → rename("queued/<id>", "claimed/<id>")   # 同目录 rename 原子
冲突     → 值班员告知："研究员刚取走，无法编辑"
```

### 4.6 前端 UI：复用现成插件 + 自研薄语义层

**结论：有现成插件，且覆盖了最难的 70%；不重写插件，只补我们特有的语义。**

候选：`@linxin666/dsh-client-ui-task-board`（npm 最新 **0.3.20**，要求 `dsh >= 0.1.5-rc.1`，**服务器正好是 0.1.5-rc.1** ✅，依赖仅 `schemastery`）

| 我们的需求 | 插件能力 |
|---|---|
| 前端可编辑 | ✅ 五列看板 + 任务详情 + 归档/恢复 |
| 持久化 | ✅ Host 权威账本 `$DSH_HOME/task-board/ledger-v2.json`，临时文件 + 原子 rename，POSIX 0600 |
| 真实执行 | ✅ Host runner 新建 DSH 会话，应用**钉住的工作区 / agent 预设 / 权限**，以 queue 模式发 Prompt |
| 审计 | ✅ 每任务 20 条执行记录 + `frozenBy`/`initiatedBy` 来源记录 |
| 定时 | ✅ 5 段 cron Host 调度器 |
| 确定性恢复 | ✅ 重启后 running execution 继续观察 |
| **防注入** | ✅ 执行卡片时强制包裹**来源声明**，提示接手 Agent 警惕卡片文本里的存储型提示注入 |
| 幂等 | ✅ 最近 256 个 request id + 动作 SHA-256 指纹持久化 |
| 安全模型 | ✅ 严格版本化判别联合；浏览器不能写 scheduler 时间戳或 execution 结果；**协议不接受 shell 命令 / 可执行路径** |
| 对外接口 | ✅ `GET /api/task-board/state` · `GET /api/task-board/events`(SSE) · `POST /api/task-board/action` |
| 不改源码 | ✅ 只通过 `cordis.patch.yml` + profile 挂载 |

**安装**：`dsh plugin --profile web add @linxin666/dsh-client-ui-task-board@latest`

#### 必须我们自己补的三处缺口

| 缺口 | 插件现状 | 补法 |
|---|---|---|
| **排队语义** | 明确写"**任务运行不并发、不排队**"；错过的 cron 触发点跳过、绝不补跑 | 排队由我们的 `requests/` 层负责；task-board 只承载"可执行卡片" |
| **tier 路由** | 无 tier 概念 | 用**钉住的 agent 预设**表达 → 定义三个预设：`duty` / `associate` / `researcher` |
| **知情拒绝（ETA / deferred_reason）** | 无对应字段 | 值班员算出 ETA 与原因，写进卡片描述或侧车文件 |

#### 两个必须知晓的风险

1. **遥测**：插件每 UTC 日向 `dsh-market.com` 发送一次匿名心跳（仅随机 ID + 包名）。服务器可能连不上；但这是**第三方网络行为**，需明确接受。
2. **第三方依赖**：`linxin666` 为社区包。它已在用户本机使用（`~/.dsh/task-board/ledger-v2.json` 存在），但在生产服务器引入需确认。

#### 容器内限制

- Linux 电源保护需 `systemd-logind` → **本容器会显示 `unsupported`**（无妨，本场景不需要防睡眠）
- 账本有**单进程锁** `ledger-v2.lock`：同一 DSH home 只能有一个 Host 进程持有账本，**不可同时起两个 DSH**

### 4.7 附带作用：交接班记录

- **研究员上线** → 读 `requests/` 找待办
- **研究员下线** → 把"期间发生了什么"写成 `source: system` 的记录
- **用户随时 `ls requests/`** 就能看到全部待办 + 历史

这实现了"研究员装载时可以直接问它期间发生了什么"——**答案就在这个目录里，不依赖模型回忆**。

### 4.8 与 §4.1–4.5 的关系

`requests/` 目录仍是**权威的排队状态**（事件溯源、可 `ls`、可脚本操作、认领语义）；task-board 是它的**可视化与执行前端**。两者通过值班员同步：

```
requests/*.json  ──值班员同步──►  task-board ledger（卡片）
      ▲                                    │
      └────── 执行结果回写 ◄───────────────┘
```

**不变量**：排队与认领的真相只在 `requests/`；task-board 不实现排队，只展示与执行。

## 5. 知情拒绝：不可用时必须给出三样东西

当用户请求需要研究员、但研究员在实验窗口外时，**值班员负责回话**，且必须给出：

```
1. 为什么不可用   → "研究员需要 GPU，当前 gsm8k-student-cod-grpo-001 正在独占显卡"
2. 还要等多久     → "已跑 2h14m，超时 4h，预计还有 ~1h46m 释放"
                    （依据 evidence/<id>/job.json 的 started_unix + timeout_seconds）
3. 你能选什么     → "A. 排队（研究员上线后优先处理，会主动回报）
                     B. 中断实验立即处理——代价：本次 run 作废需重跑"
```

**第 3 条 B 的代价是硬事实**：`train.py` 明确 `if resume: raise NotImplementedError(...)`，中断 = 彻底作废，一个正式 run 实测 **17064 秒（4.7 小时）**。值班员必须说出这个数字。

## 6. 确定性优先：不给模型添不必要的活

不必交给模型判断的，就不要交：

| 用户说 | 谁来处理 | 为什么 |
|---|---|---|
| "现在跑到哪了" | **值班员 · 查表** | 读 `job.json`，不需要推理 |
| "中止实验" | **值班员 · 规则匹配** + 确认 | 纯确定性动作 |
| "列一下还没跑的实验" | **值班员 · 查表** | 对比 `matrix.json` 与 `results/` |
| "为什么 loss 在第 40 步突增" | **值班员 · 智力操作** | 要理解摘要（R1/R2 已实测可用） |
| "给这个 run 画图" | **值班员 · 智力操作** | 选脚本、传参 |
| "速记法为什么老是退化，怎么办" | **研究员** | 要读协议、做研究判断 |

**中止是安全敏感操作**，加一道确认：

```
值班员识别意图 → 回显"将中止 X，代价：本次 run 作废，损失 2h14m 算力" → 等用户确认 → 执行
```

执行本身是纯确定性的（kill 进程组 → 等 `release_timeout_seconds` → 核对 `gpu-release.json`），**不依赖模型判断**。

## 7. 日志处理原则

**不把原始日志喂给模型。** lab 已产出结构化产物：

| 产物 | 内容 |
|---|---|
| `metrics.jsonl` | 每步 reward / grad_norm / entropy / KL / clip / 吞吐 / 显存 |
| `groups.jsonl` | 组零方差率、全错/全对分解、组内成功数分布 |
| `validation.jsonl` | 每步 dev val_acc |
| `job.json` | 状态 / 退出码 / 耗时 |

**确定性摘要器**把一次 4.7 小时的训练压成 1–2k token，再由模型解读。这样连小模型都够用，且摘要可复算、可审计。

## 8. 核心不变量

> **无论哪一层不可用，值班员都能给出"为什么 + 多久 + 你有哪些选项"。**

这就是"值班"的全部意义——它不是最弱的那个，它是**唯一保证在场**的那个。
